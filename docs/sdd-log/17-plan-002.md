# 17 - Plan 002

**Command:** /speckit-plan
**Spec Kit:** v1.1.4.dev0 · **Date:** 2026-10-17

## Prompt
/speckit-plan Plan feature 002 (USD valuation). Follow the conventions
established by feature 001's code and plan (stack, layers, config, error
handling, tests); don't restate them. Treat the following as decisions;
research only items marked OPEN.

Price source: CoinGecko /coins/{id}/history, coin id and base URL from
config (legacy keys coingecko_url, coin_id), USD only.
API key: optional, config file only (like the wallet password), sent in
the header the legacy code uses; never in any output.
Precision: parse prices from the JSON response as Decimal, never float.

History period: skip days older than 364 days (one day of margin inside
the documented 365). Classify responses: HTTP 401 with error_code 10012
means "outside history"; any other 401 means the key was rejected; 429
means rate limited. Read the body before classifying a 401.
Rate limits: on a 429, retry once after a short backoff, then stop
pricing for the rest of the run.
Pacing: OPEN, the request interval needed to stay within the public and
demo tiers' limits; legacy default was 1.2 s, configurable
(min_request_delay). Verify against SC-007.
Order: oldest day first.

Settling: a day is settled 1 hour after its UTC end (source publishes at
~00:35 UTC). Store a status (provisional/final) and a source (api/import)
with each price.
Storage: a daily_prices table keyed by UTC date (YYYY-MM-DD), price stored
losslessly as decimal text, with status, source, and when it was fetched.
Add it with a migration from schema version 1 to 2 (PRAGMA user_version).
Compute transaction USD values from amount and price when needed; do not
store them.
Import (P3): --import-prices PATH reads the CSV described in the spec
(stdlib csv module; parse prices as Decimal); validate the whole file
before writing anything, then insert in one transaction.

Scope: feature 002 only. No CSV output or summaries.

## What Came Back
I wrote the plan and design artifacts for feature 002. One finding needs your decision before /speckit-tasks, and two of your decisions couldn't be checked against the legacy code from here.

1. SC-012 can't be met without an API key (research R1). That's the open pacing question you asked me to research. CoinGecko's documented limits are:
- No key: about 10–30 requests a minute, varying with server load.
- Free Demo key: 100 requests a minute (older third-party docs say 30).

/history returns one day per request, so staying within those limits sets the pace:

┌───────────────────────────────┬───────────────┬─────────────────────────────┐
│   Interval between requests   │ 365 days take │ Meets SC-012 (under 5 min)? │
├───────────────────────────────┼───────────────┼─────────────────────────────┤
│ 0.7 s (default with a key)    │ ~4 min 16 s   │ Yes                         │
├───────────────────────────────┼───────────────┼─────────────────────────────┤
│ 6.0 s (default without a key) │ ~36 min       │ No                          │
├───────────────────────────────┼───────────────┼─────────────────────────────┤
│ 1.2 s (legacy default)        │ ~7.3 min      │ No, even with a key         │
└───────────────────────────────┴───────────────┴─────────────────────────────┘

So I didn't keep 1.2 s as the default. The plan uses 0.7 s with a key and 6.0 s without, and
min_request_delay overrides either. Without a key, SC-007 (no rate-limit refusals) and SC-012
can't both hold.

The options for the spec:
- (a) Recommended: make SC-012 apply only when an API key is configured. A Demo key is free.
- (b) Switch to an endpoint that returns many days per request. This contradicts your /history
  decision and returns different price points.
- (c) Drop SC-012.

2. Two decisions I couldn't check against the legacy code. The legacy analysis is in
docs/sdd-log/, which I'm not allowed to read.
- API key header: I used x-cg-demo-api-key, the header CoinGecko documents for Demo keys.
  Please confirm it's what the legacy code sends.
- error_code 10012 for "outside history": this code isn't in CoinGecko's current public error
  list. I kept it as you decided. If CoinGecko signals out-of-range dates some other way, 
  pricing would stop early with a "key rejected" warning rather than record anything wrong. 
  The 364-day cutoff should make this rare.

3. Things the docs confirmed that the design depends on:
- What the daily price is: the price for date D is CoinGecko's snapshot at 00:00 UTC, the start
  of D, published at about 00:35 UTC. Your rule (settled 1 hour after D ends) keeps D
  provisional all day, so each day gets one extra refresh before it's finalized. That's conservative,
  not a bug.
- Exactness: httpx's .json() returns floats, so the client decodes with json.loads(…, parse_float=Decimal).
  Python's default decimal precision (28 digits) can silently round amount × price, so valuation runs
  with a wider precision and raises if any rounding would happen.

4. Choices I made that weren't in your input:
- API key config name: coingecko_api_key. The legacy name is unknown for the same reason as above.
- Rate-limit backoff: 10 seconds, or a Retry-After value up to 60 seconds if CoinGecko sends one. 
  The docs don't say whether it does.                                                     
- Database triggers: they block updating a final price and deleting any price, as a second guard behind the code.
- SyncResult becomes RunResult (sync count, import summary, pricing summary). Feature 001's CLI and tests that 
  build it are updated in the same change.
- Output wording: the new summary lines and stop warnings are in contracts/cli.md.

## Answers
Use the following as decisions and update the plan as needed.

For 1, go with the recommended option - a.

The legacy code uses the header `x-cg-pro-api-key`.  Its assumption was that a key
was only needed for the pro API.  The config file should set the header or key type
as well as the key.  Both can be overridden on the command line.

The error_code 10012 was discovered today with a manual test.
```
❯ curl -s "https://api.coingecko.com/api/v3/coins/monero/history?date=01-01-2024"
{"error":{"status":{"timestamp":"2026-10-17T14:00:34.302+00:00","error_code":10012,"error_message":"Your request exceeds the allowed time range. Public API users are limited to querying historical data within the past 365 days. Upgrade to a paid plan to enjoy full historical data access: https://www.coingecko.com/en/api/pricing. "}}}%
```

## What Came Back
I applied all three decisions to the plan artifacts and to the spec's SC-012. Nothing is leftblocking /speckit-tasks.

1. SC-012 (option a). The spec now says SC-012 applies when an API key is configured, with a Clarifications entry. That's the one spec change. Research R1 is marked resolved. Keyless runs stay within the keyless limits at about 6 seconds per request and just take longer.            

2. Key type, configured with the key:
- Config: coingecko_api_key and coingecko_api_key_type (demo or pro). The type is required whenever a key is set, so the header is never guessed. A key without a type is an error.
- Command line: --coingecko-api-key and --coingecko-api-key-type override the config file.
- The type picks the header: demo sends x-cg-demo-api-key; pro sends x-cg-pro-api-key, the legacy header. Legacy users set pro.
- It also picks the default base URL. CoinGecko serves Pro keys from pro-api.coingecko.com, and Demo and keyless requests from api.coingecko.com. An explicit coingecko_url still wins. Without this, a Pro key sent to the public host would fail.
- A key given on the command line still never appears in the tool's output (FR-015). It can show up in your shell history and in process listings, so the contracts and the planned README text recommend the config file.

3. error_code 10012. Research R3 now records your manual test and the body it returned. The client reads error.status.error_code, and also accepts status.error_code or a top-level error_code. Your test also confirms the 365-day limit applies to keyless use.

Two things still worth checking:
- The HTTP status of the 10012 response. curl -s doesn't print it, and the plan classifies only a 401 carrying 10012 as "outside history," per your decision. If the real status is different, pricing would stop with an "unavailable" warning rather than record anything wrong. A one-off curl -s -o /dev/null -w '%{http_code}' … would confirm it.
- The 364-day cutoff applies even with a Pro key, as you decided. Paid plans have longer history, so a Pro user's older days could be looked up. Lifting the cutoff for Pro keys would be a separate decision, noted in research R3.
