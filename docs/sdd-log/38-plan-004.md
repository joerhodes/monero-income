- No new dependencies (R2). With no setting, local dates come from astimezone(None), which handles daylight-saving changes correctly for each transaction. Zone names are checked against the system's time zone database. The check is case-sensitive so macOS and Linux behave the same.

Design changes

- Its own read. The summary step reads its records with a second read through a new summary_reader hook in run(). It runs right after the export's read, before anything is committed, so both see the same data (FR-019). If it fails, the export is still written and the run fails afterwards. This replaces the single shared read I had planned, and feature 003's export step stays exactly as it is.
- Three guarded stages.
  - Reading: the summary read itself.
  - Computing: build_summaries first checks each record (non-negative amount, a valid moment, a price that is absent or finite and positive, a status that matches the price) and raises SummaryDataError with the transaction id.
  - Rendering: the renderer checks its input the same way.

  Any failure, including a bug, becomes SummaryError. It carries the run's results so the CLI can still print the earlier lines.
- No partial output. The CLI builds the complete summary lines before printing anything. On a failure, stdout has only the earlier lines, ending with Exported …, and stderr gets Error: cannot show the income summaries: <reason>. The export was written to <path>; recorded transactions and prices were kept.
- Ctrl-C still exits 130 with feature 001's message, as before.

Tests planned. One injected failure per stage:
- Reading: a reader that raises StorageReadError("invalid stored price 'abc'"), and one that raises RuntimeError.
- Computing: records with a NaN price, a negative amount, or a status without a price.
- Rendering: a malformed summaries object, and a renderer that raises.

Each test checks the earlier lines, the single error line, exit status 1, and an export byte-identical to the one the run wrote.

One difference from your example: a real unparseable stored price in the database can't reach the summary step. The export's own read rejects it first, so the run fails under feature 003's rules: no lines printed and no export written. The FR-018 tests therefore simulate it through the injected reader. I recorded this in research R1 and contracts/cli.md. Say if you want something different.
