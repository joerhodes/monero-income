# 26 - Plan Spec 003 - Transaction Export

**Command:** /speckit-plan
**Spec Kit:** v1.1.4.dev0 · **Date:** 2026-10-26

## Prompt
/speckit-specify monero-income records a Monero wallet's incoming
transactions (feature 001) and values them in USD (feature 002). This
feature writes a transaction export: one CSV file listing every recorded
transaction with only its essential data. It serves two purposes: a
record for a financial audit, and an additional, human-readable 
backup layer. Summaries (monthly CSV and on-screen reports) are a 
separate, later feature. Restoring from the export is out of scope.

Behaviors:
- Every run that completes sync and pricing writes the export, even if
  some days could not be priced. If the sync fails, or the run fails
  with an error, no export is written.
- Each run replaces the previous export. An interrupted or failed write
  never leaves a partial file; the previous export stays intact.
- The file is `xmr_income.csv` in the configured output directory.
- The output directory is read from the configuration with the key 
  `reports_path` and defaults to `~/reports`.  This may can also be 
  specified as a command option.
- One row per recorded transaction, oldest first, with a header row.
  Columns, in order:
  - txid: the transaction id
  - height: the block height
  - timestamp_utc: the moment of the transaction, ISO 8601 in UTC
  - xmr: the exact amount, always 12 decimal places
  - usd_price: the USD price of 1 XMR for the transaction's UTC day, at
    full recorded precision; TBD if the day has no price
  - price_status: final, provisional, or TBD
  - usd_value: xmr times usd_price, rounded to the nearest cent; TBD if
    the day has no price
- Except for usd_value, every value is exact: together, the columns
  contain everything needed to rebuild the recorded transactions and
  prices without loss.
- No value is written in scientific notation or with thousands
  separators.
- The export's columns and their meanings are documented for a reader
  who has never seen the tool.

What's in it: four user stories.
1. Export after each run (P1): written whenever sync and pricing complete, and not written when the run fails.
2. Never a broken file (P1): each run replaces the export in full. An interrupted or failed write leaves the previous export intact.
3. Output directory (P2): the --reports-path option, then the reports_path config key, then ~/reports.
4. Documentation for a new reader (P3).

There are 25 functional requirements and 8 success criteria. I checked one acceptance scenario by hand: 1.234567890123 XMR × 152.3456 gives a usd_value of 188.08.

Defaults I chose rather than asking. These are in the spec's Assumptions section, and any of them can change in /speckit-clarify:
- Row order: by timestamp, then block height, then txid. Block timestamps don't always increase with height, so I sorted by the time a reader sees.
- Rounding: usd_value is rounded half up, to exactly 2 decimals.
- No transactions: the file has only the header row.
- Missing directory: created, including any missing parent directories.
- Write failure: the run shows an error and ends with a failure status. Transactions and prices recorded earlier in the run are kept.
- New output line: the run reports the export's full path and row count. You didn't ask for this; it's the only change to existing output.
- TBD: covers both temporarily unpriced days and days older than the price history. The run's own messages already tell them apart.
- Price origin: whether a price came from the price source or an import isn't exported, so "rebuild without loss" means transactions plus each day's date, price and status.
- Deferred to planning: line endings and where the column documentation lives. The constitution's golden-file tests then lock the format.
